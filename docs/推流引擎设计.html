一、先把抖音的机制拆成 5 个可实现的部件

调研抖音推流机制后，能落地的就这 5 块，别被"玄学"吓住：

# 抖音机制 我们的实现 难度
1 多路召回（协同过滤/内容/热点/关注） 7 路并行召回 → 候选池 ⭐⭐
2 排序公式：推荐得分 = 预测行为概率 × 行为价值权重 加权打分函数 ⭐⭐⭐
3 流量池赛马（逐级晋级） 状态机 + 定时晋升任务 ⭐⭐⭐⭐ 最难
4 重排打散（探索位/去重/疲劳度） 重排规则 ⭐⭐
5 实时行为回写 事件表 + 画像更新 ⭐

💡 重要认知：抖音 2026 的官方口径是 推荐得分 = 预测用户行为概率 × 行为价值权重 注意前半段是"预测"，不是"统计"。我们第一版做统计版（用历史实际率代替预测概率），第二版再接预测模型。不要一上来就上深度学习。

二、流量池赛马机制（本项目最核心的原创设计）

2.1 抖音的流量池层级（多来源交叉验证）

层级 曝光量 主要考核指标
冷启动池 200–500（部分来源 300–1000） 2秒/3秒留存、初始完播
初级池 3,000–5,000（1,000–5,000） 完播率≥28~30%、原创度
中级池 1万–10万（5,000–3万） 互动率、收藏率、转发率
高级池 10万–100万（3万–50万） 转化率、留存时长
爆款池 100万+ 综合权重高于行业均值

赛马本质：同一时间段，系统把同标签内容放进流量池 PK 数据，胜出者晋级15。

2.2 ⭐ 迁移到 GitHub 仓库：这是全项目最关键的一步

核心问题：视频是"一次性消费"，仓库是"长期资产"。仓库没有"完播率"这种天然指标。

我的方案：给每个仓库也建流量池，但晋级指标要重新定义：

仓库进入候选池 │ ┌─────────▼─────────┐ │ 冷启动池 (quota 200) │ │ 考核：CTR + 3秒留存 │ └─────────┬─────────┘ │ ctr ≥ 0.06 且 not skip-heavy ┌─────────▼─────────┐ │ 初级池 (quota 2000) │ │ 考核：深读率 ≥ 0.30 │ ← 等价"完播率" └─────────┬─────────┘ │ deep_rate ≥ 0.30 ┌─────────▼─────────┐ │ 中级池 (quota 2万) │ │ 考核：star率 ≥ 0.03 │ ← 等价"收藏率"（最高权重） └─────────┬─────────┘ │ star_rate ≥ 0.03 或 评论深度达标 ┌─────────▼─────────┐ │ 高级池 (quota 20万) │ │ 考核：综合分 + 长尾 │ └─────────┬─────────┘ │ 爆款池（全站）

指标等价映射表（这是本项目的原创贡献）：

抖音指标 权重(2026) 我们的等价指标 埋点定义
收藏率 25%（最高） star 转化率 点击「去 GitHub star」且真的跳转了 / 曝光数
复访率 高 重复访问率 同一用户 7 天内二次打开该仓库
铁粉互动 高 关注作者 / 高频用户互动 follow_owner 事件
5秒完播 中 3秒停留率 卡片停留 ≥3s / 曝光数
整体完播 中（已降权） README 深读率 scroll_depth ≥ 0.5 / 曝光数
评论质量 中 评论长度 ≥15字 body_len 统计
点赞 低（已降权） 网页端点赞 like 事件
转发 低 分享链接 share 事件

🔑 反直觉但重要：抖音 2026 已经把 完播率从 35% 降到不足 10%，把 收藏率提到 25%35。 这对我们是天大的好消息 —— 因为仓库的"收藏"就是 GitHub Star，而且 star 是可以真实校验的（比点赞更难刷，信号质量远高于抖音的收藏）。 推论：我们的推流引擎应该以 Star 转化率为第一核心指标，而不是停留时长。

2.3 7 天长效赛马（2026 新规，必须抄）

抖音 2026 最大变化：从"24小时定生死"改成"7天长效推流"25。

阶段1（1-2天）：冷启动，考核 3 秒停留 阶段2（3-4天）：二次激活，看收藏、复看 阶段3（5-7天）：长尾爆发，铁粉+搜索流量加持

对我们意味着什么：一个被遗忘 3 年的老仓库，只要开始被人收藏（star）、被人复访，就应该被重新推上去。

⭐ 这正好是"挖坟效应"的代码化 —— 抖音用来救老视频，我们用来救老仓库。这是把抖音机制直接嫁接到你的核心诉求上，完美契合。

配套要求：7 天内禁止删除/隐藏（抖音规则）。我们对应的是：晋级期内仓库不能被清理出池，且要有"复活"通路。

各路实现细节

通路 面向 查询逻辑 配额
① 兴趣召回 主力 按 user_profiles.top_topics / top_languages 匹配 repos.topics/language 150
② 遗珠召回 ⭐ 本项目特色 forgotten_score DESC 且 曝光数 < 阈值 80
③ 热榜召回 大众 velocity_score DESC（Star增速，不是总 star） 80
④ 新鲜召回 新仓库 created_at_gh > 7天前 且 quality_score > 阈值 60
⑤ 关注召回 老用户 repos.owner IN (用户 follow 的 owner) 40
⑥ 探索召回 所有人 随机 + 多样性约束 60
⑦ 相似召回 有历史 item-based CF：「看了 A 的人也在看 B」 60

-- 遗珠召回：找"优质但被埋没"的仓库 SELECT r.* FROM repos r JOIN repo_pools p ON p.repo_id = r.id WHERE r.forgotten_score > 0.5 AND p.impressions < 500 -- 曝光少 = 被埋没 AND r.is_archived = 0 AND r.is_dead = 0 AND r.id NOT IN ( SELECT repo_id FROM feed_impressions WHERE user_id = ? AND shown_at > datetime('now','-7 day') ) ORDER BY r.forgotten_score DESC LIMIT 80;

四、打分公式（精排核心）

4.1 主公式

python
def score_repo(user, repo, ctx, weights) -> float: """ 推荐得分 = 预测行为概率 × 行为价值权重 第一版用"统计率"代替"预测概率" """ # ── 第一项：多目标行为预估（迁移自 2026 抖音权重体系）── eng = ( weights['w_star'] * repo.star_rate + # 收藏率 25% ← 最高 weights['w_deep_read'] * repo.deep_rate + # 深读率 35% weights['w_comment'] * repo.comment_rate + # 评论 12% weights['w_share'] * repo.share_rate + # 分享 10% weights['w_like'] * repo.like_rate + # 点赞 8% ← 已降权 weights['w_follow'] * repo.follow_rate # 关注 10% ) # ── 第二项：时效衰减（指数衰减，越新越占优）── recency = exp(-weights['recency_decay'] * repo.hours_since_pushed / 24) # ── 第三项：Star 增速加成（解决"老仓库霸榜"）── velocity = log1p(repo.stars_per_day) * weights['velocity_boost'] # ── 第四项：⭐ 遗珠加成（本项目特色，与商业平台相反）── forgotten = repo.forgotten_score * weights['forgotten_boost'] # ── 第五项：用户个性化匹配 ── affinity = ( 0.5 * topic_match(user.top_topics, repo.topics) + 0.3 * language_match(user.top_languages, repo.language) + 0.2 * owner_affinity(user.affinity_owners, repo.owner) ) # ── 第六项：多样性惩罚（避免全是同一语言）── penalty = diversity_penalty(ctx.session_languages, repo.language) return (eng + velocity + forgotten) * recency * (1 + affinity) * penalty

4.2 参数默认值（已写入 algo_config 表，可热调）

w_deep_read = 0.35 # 深读率（≈完播） w_star = 0.25 # ⭐ star 转化（最高） w_comment = 0.12 w_share = 0.10 w_follow = 0.10 w_like = 0.08 # 已降权 recency_decay = 0.08 velocity_boost = 1.5 forgotten_boost = 1.8 # ⭐ explore_rate = 0.15

五、重排阶段（抖音最精妙的一步）

5.1 打散规则

调研结论6：抖音重排会"每两个硬核内容中间插一个轻松内容，防止疲劳"，本质是 Explore vs Exploit。

python
def rerank(candidates, user, n=20): out, used_langs, used_owners = [], set(), set() for i in range(n): # 每 5 条插入 1 条探索内容（15% ≈ 3/20） if i % 5 == 4: pick = random_exploration(candidates, exclude=out) else: pick = best_valid( candidates, exclude=out, # ⭐ 打散：同语言/同作者不能连续出现 ban_langs = used_langs if i>=1 else set(), ban_owners = used_owners if i>=1 else set(), ) if not pick: break out.append(pick) used_langs.add(pick.language) used_owners.add(pick.owner) return out

sql

5.3 疲劳度衰减（2026 新增）

抖音 2026 模型引入了「用户疲劳度衰减因子」，对同质化内容降权4。 实现：统计用户最近 N 条曝光里各语言的占比，超阈值则乘惩罚系数。

六、冷启动方案（新用户 + 新仓库 + 老仓库）

场景 问题 方案
新用户 没有画像，不知道推什么 「摸底 5 条」：推 5 个覆盖不同语言/领域的高质量仓库，快速建立初始画像。之后放开兴趣召回
新仓库 没有行为数据，协同过滤召回不到 走 内容召回（topics + README embedding），不走 CF
老仓库 ⭐ star 少、无人问津 走 遗珠召回 + 7天长效赛马复活通路
无 star 快照 算不出 velocity 降级公式：log1p(stars) / (age_hours + 1)

冷启动判定（users.is_new_user）：interest_count < 10 视为冷启动中。

八、实施顺序建议（避开"半途而废"）

阶段 1：能刷起来（1~2 天） 1. 建表（跑 schema.sql） 2. 灌 200 个仓库的假数据 / 真实数据 3. 只实现 ①兴趣 + ③热榜 + ⑥探索 三路召回 4. 打分公式用最简版（只有 eng + recency + affinity） 5. 前端能滑起来

阶段 2：能赛马（2~3 天） 6. 加 repo_pools 状态机 + 晋级定时任务 7. 埋点全链路打通（曝光必埋，否则算不出率） 8. 加 repo_star_snapshots 定时任务 → 算出 velocity

阶段 3：有特色（2~3 天） 9. 加 ②遗珠召回 + forgotten_score 计算 10. 加重排打散 / 疲劳度 11. 加 7 天长效复活通路

阶段 4：变聪明（后续） 12. 用户画像向量化（双塔召回） 13. 把统计率换成模型预测
