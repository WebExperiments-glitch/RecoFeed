## 二、修复清单

### ① `repo_pools` 缺 `follows` 列 → 所有召回直接崩 ⚠️ 致命

**现象**：`sqlite3.OperationalError: no such column: p.follows`

**根因**：`recall_trending` 等 7 个通道共用的 `_SELECT` 里读 `p.follows`，
但 `repo_pools` 表根本没这一列 —— "关注"在本系统里是**关注作者**
（独立 `follows` 表），不是仓库级计数。

**修复**：改为 LEFT JOIN 现算
```sql
CASE WHEN f.owner IS NULL THEN 0 ELSE 1 END AS follows
LEFT JOIN (SELECT DISTINCT owner FROM follows WHERE user_id = :uid) f
       ON f.owner = r.owner
```

**踩坑**：`sqlite3.execute()` 只接受**一个**参数容器，
不能写 `execute(sql, (a,b), {"uid":1})`。统一用 `_bind()` 把
位置参数 + `uid` 合并成单一 dict，SQL 里的 `?` 全部改为 `:q0/:q1/...`。

---

### ② `tags_json` 列不存在 → 整条推荐链路静默失效 ⚠️ 致命

**现象**：所有候选仓库的 `tags` 都是空的，搜索干预、兴趣召回、
画像匹配**全部静默失效**——不报错，只是永远返回空结果。

**根因**：schema 里压根没存标签的地方。`_row_to_candidate` 读
`row["tags_json"]` 永远拿不到东西。

**修复**：
- schema 的 `repos` 表新增 `tags_json` + `tags_updated_at` 两列
- 灌数据时用 `extract_readme_tags()` 提取并缓存

> **为什么必须落库缓存**：jieba 提取一个 README 约 3~8ms，
> 每次 Feed 请求对几十个候选重新提取会让响应时间爆炸。

**效果**：候选标签从 `0/29` 变为 **`29/29`**。

---

### ③ 停用词表被 `│` 污染

**现象**：`│ ── 符号噪声 ──` 这行少了 `#` 注释符，
导致 `│`、`──`、`符号噪声` 本身被当成停用词加载。

**修复**：补上 `#`，同时清理 jieba 解析残留的 `.stop_words.resolved.txt` 缓存。

---

### ④ 时效衰减无下界 → 遗珠仓库被打成 0 分 ⚠️ **本项目最严重的缺陷**

**现象**：11 个遗珠候选**全部** `recency = 0.000`，最终得分 `1e-29`。
一个 `hexo-lite` 的遗忘分高达 1.728（全池最高），却因为衰减被彻底抹杀。

**根因**：
```python
exp(-0.08 × 700 天) = e⁻⁵⁶ ≈ 5e-25
```
`recency_decay` 用的是**无下界**的指数衰减。仓库越久没更新，
衰减越狠 —— 而"久没更新"恰恰是遗珠召回要救的对象。

> **这个 bug 精准地干掉了本项目唯一的存在理由**：
> 想救落灰仓库，却用一条公式把所有落灰仓库判了死刑。

**修复**：分段衰减 + 保底
```python
knee = 90 天
if days <= knee:
    return exp(-0.08 × days)          # 正常时效排序
return max(0.35, knee_val × exp(-0.0015 × (days - knee)))
```
保底 0.35 的含义：老仓库最多损失 65% 时效分，不再归零。

**效果**：遗珠仓库得分 `0.0` → `0.59 ~ 0.67`。

---

### ⑤ 新仓库 engagement 恒为 0 → 永无出头之日 ⚠️ 自锁死循环

**现象**：率值 = 行为数 / 曝光数，新仓库曝光数是 0，
所以 `star_rate`、`deep_rate`… 全是 0，`engagement = 0`。

**这是个逻辑闭环**：
```
没有曝光 → 行为数为 0 → 得分 0 → 排最后 → 拿不到曝光 → ...
```

**修复**：无曝光时退回用质量分当先验
```python
if c.impressions <= 0:
    return c.quality_score * 0.6   # 新仓库预期约为同质量老仓库的 60%
```

---

### ⑥ 去重窗口一刀切 → 池子小时刷两轮就空屏

**现象**：29 个仓库全部进过 7 天去重窗口后，
`/api/feed` 返回 `reason: no_candidates`，**空屏**。

**根因**：`_exclude_recent` 硬性排除 7 天内看过的，
自建部署的仓库池往往只有几十个，两轮就刷空了。

**修复**：去重降级阶梯 `7天 → 1天 → 不过滤`，
阈值改为池子规模的 40%（而非固定常数 30，
否则 29 个仓库的池子永远够不到门槛，每次都降到全量不去重）。

> 设计取舍：**宁可轻微重复，也不能空屏。** 空屏比重复严重得多。

---

### ⑦ 遗珠仓库排序永远垫底 → 配额只给到末尾 ⚠️ 产品主张问题

**现象**：修完 ④ 之后遗珠不再 0 分，但仍在全池第 19~29 位，
**永远进不了前 10**。

**根因**：热门仓库的 `velocity` 分项单项就有 **0.96**，
而遗珠加成上限只有 **1.8**。加分只能"拉近差距"，拉不平差距。

**修复**：两类互补措施
1. **保底席位配额** —— 每次 Feed 强制给遗珠 2 席、新仓库 1 席
2. **席位插在中段**（约 1/3、2/3 处），而非末尾

> 第 2 点是细节但重要：塞在第 9、10 位等于告诉用户"这是凑数的"，
> 曝光质量远低于穿插展示。

**效果对比**：

| | 修复前 | 修复后 |
|---|---|---|
| 遗珠最高排名 | 第 19 位 | **第 4 位** |
| 遗珠得分 | 0.000 | 0.659 |
| 通道标记 | `forgotten` | `forgotten,trending,explore,quota` |

# 第二轮修复：缓存池架构 + 搜索

> 上一轮把后端从"跑不通"推到"14 个接口通过"。
> 本轮做两件事：**把 Feed 改成缓存池推流**，**加搜索**。
> 过程中又挖出 **10 个真实缺陷**，其中 3 个是设计层面的。

## 五、缓存池架构（用户需求落地）

### 需求原文

> 「抓一些 GitHub 的东西先进缓存池，用户边刷缓存池边添加。
> 用户刷完的东西会被删掉。」
> 「快见底时，就是还有 6 个内容的时候，爬虫看一下用户的指标和数据，然后爬。」

### 实现

```
┌─────────┐   定向补货    ┌──────────┐   取走即删    ┌────────┐
│  爬虫   │ ───────────→ │ 待刷队列 │ ───────────→ │  用户  │
└─────────┘   (按画像)   └──────────┘              └────────┘
                              ↑
                      剩 ≤6 条触发补货
```

| 文件 | 职责 |
|---|---|
| `feed/queue.py` | 队列读写。`pop_queue()` 取走即删**队列项**，仓库本体保留 |
| `feed/refill.py` | 定向补货。`build_fetch_plan()` 按画像决定"抓什么" |
| `feed/service.py` | 主入口。取队首 → 见底补货 → 实时保底（绝不空屏） |
| `jobs/test_queue.py` | 端到端验证（事务回滚，不污染数据） |

### 新增 API（4 个）

| 接口 | 说明 |
|---|---|
| `GET /api/stats/queue` | 队列水位 + 最近补货记录 |
| `POST /api/queue/refill` | 手动补货（"换一批"） |
| `POST /api/queue/rebuild` | 清空重灌（"重置推荐"） |
| `GET /api/feed` | 改为走队列（带 `search` 参数时走实时管线） |

### 验证结果

```
① 首次进队列   队列 0 → 30 条（自动灌池）
② 用户刷卡     30 → 26 → 22 → 18 → 14 → 10（每次正好减 4）
               刷过 20 条全部唯一，无重复
               刷过的仓库本体 20/20 保留，repos 总数 84 未变
③ 低水位触发   剩 5 条 → is_low=True → 补货 → 5 → 60
④ 补货日志     每次水位/抓取量/入队量/方向都有记录
⑤ 定向性       抓取方向与画像有交集（非盲目）
⑥ 极端情况     队列清空仍返回 8 条（实时保底）
```

## 六、搜索（用户需求）

### 需求原文

> 「后端要加一个搜索按钮」

### 为什么不能复用原来的 `build_feed(search_query=...)`

原来的"搜索"本质是**先跑 7 路个性化召回，再给命中搜索词的候选加点分**。
召回集合里没有"匹配关键词"这个约束，加多少分都救不回来。

实测（修复前）：

| 查询 | 返回结果 | 问题 |
|---|---|---|
| `rust` | tailwindcss、chroma、duckdb | 候选池里根本没约束 rust |
| `vector database` | ui-tars、vuejs/core | 完全不相关 |

### 实现：`api/search_service.py`

全库扫描 + 9 层匹配打分，与个性化无关：

| 层 | 匹配方式 | 分值 |
|---|---|---|
| ① | 名称完全匹配 | +6.0 |
| ② | 名称包含 / 全名匹配 | +4.0 / +3.0 |
| ③ | 简介含搜索短语 | +2.5 |
| ④ | 语言精确匹配 | +3.0 |
| ⑤ | topics 命中 | +2.2 / +1.1 |
| ⑥ | 技术标签命中（按权重加权） | +2.0~3.0 |
| ⑦ | 分词全命中 / 部分命中 | +1.8 / +0.6×n |
| ⑧ | 简介逐词命中 | +0.4×n |
| ⑨ | README 正文命中 | +0.35×n |

> ⭐ 第⑨层是中文查询的关键：中文标签太稀疏（84 个仓库只有 8 个带中文标签），
> 没有 README 正文匹配的话，搜"量化""推理"几乎无结果。

### 新增 API（3 个）

| 接口 | 说明 |
|---|---|
| `GET /api/search` | 搜索。支持分页 / 语言筛选 / 最低 star / 4 种排序 |
| `GET /api/search/suggest` | 联想词（语言 + 标签 + topics） |
| `GET /api/search/hot` | 热门词（空搜索框默认展示） |

排序选项：`relevance`（默认）/ `stars` / `recent` / `forgotten`（遗珠优先 ⭐）

### 验证结果（修复后）

| 查询 | 返回 Top3 |
|---|---|
| `rust` | **rust-lang/rust、too-many-linked-lists、ruff** ✅ |
| `vector database` | **duckdb、chroma、clickhouse** ✅ |
| `sqlite` | **sqlite-vec-demo、litefs、sqlite** ✅ |
| `量化` | **gguf-spec、o2、stable-diffusion-cpp** ✅ |

排序实测：`sort=forgotten` 出 200~430★ 遗珠，`sort=stars` 出 ollama(112000★)。
分页实测：offset 0/4/8 各 4 条，无重复无重叠。

## 七、本轮修复的 10 个缺陷

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | **停用词表缺英文通用词** | `running`/`large`/`local`/`simple` 拿到与 `gguf`/`inference` **相同的 TF-IDF 权重**，全灌进标签 | 停用词 52 → 1035 条，补全语法词+通用形容词+README 套话 |
| 2 | **停用词表缺中文语法词** | `为什么`/`每个`/`某个`/`一步`/`直接` df 高达 5~9，挤占真技术词 | 补中文语法词、程度副词、切词碎片 |
| 3 | **`platf` + `orm` 碎片化** | `Supported` 不在 jieba 词典被切碎，两片都拿 0.2717 分 | `tech_terms.txt` 补 100+ 英文整词 |
| 4 | ⭐ **README 长度偏差** | elasticsearch README 仅 6 词 → 每词归一后 1.71；ollama README 长 → 最高词才 0.56。**短 README 仓库凭词少就赢**，把 `search`/`engine`/`restful` 顶进画像 Top3 | 新增 `_rerank_within_repo()`，每个仓库标签先归一到自身最大值 |
| 5 | ⭐ **补货方向混入项目名** | `_high_conversion_tags()` 没过滤仓库名派生词，`dspy`/`cpython` 以 0.54/0.39 转化率变成"技术方向" | 新增 `_self_tags_of()` + `_is_generic()`，与画像侧同一口径 |
| 6 | **数据规模不足** | 29 个仓库撑不起缓存池：灌不满 30 条、刷两轮见底、实时保底重复推 | 种子扩到 84 个，覆盖 12 个技术方向 |
| 7 | **`SEARCH_QUALITY_WEIGHT` 缺失** | 新增搜索服务引用不存在的配置项 | `core/config.py` 新增搜索段 4 个参数 |
| 8 | **重复种子冲突** | 扩容时 `sveltejs/svelte`、`ggml-org/llama.cpp` 与原种子撞名 | 分别改为 `frontend-perf/render-cost-profiler` 等 4 个新条目 + `ggml-org/gguf-spec` |
| 9 | **停用词表被误编辑** | 一次 Edit 把手滑留下的 `why-words`、超长串写进词表 | grep 校验后修正（**教训：每次 Edit 必须验证**） |
| 10 | **搜索与推荐目标混淆** | 给质量分过高权重 → 搜 `rust` 出 tailwindcss | 质量分权重压到 0.35，匹配度始终是主排序依据 |

# 第三轮修复：200 条压测暴露的问题

> 触发方式：用户要求「高强度测试，刷 200 条，关键词是 Ai、RVC，然后看匹不匹配」

压测脚本 `jobs/stress_200.py`，结果与修复记录如下。

## 一、压测暴露的 4 个真问题

| # | 现象 | 根因 | 严重度 |
|---|---|---|---|
| 1 | 队列从第 5 轮起恒为 0，16/20 轮靠实时保底 | 补货失败也刷新 30 秒冷却，队列只出不进 | 🔴 高 |
| 2 | 重复率 70.5% | 94 个仓库刷 200 条，且 `recent` 硬排除导致候选枯竭 | 🟡 中 |
| 3 | AI 匹配 61~66%，语音仅 14~20% | 补货方向里没有语音词 | 🟠 中高 |
| 4 | 搜 `Ai` 命中 `tailwindlabs/tailwindcss`；搜「向量数据库」0 结果 | 子串假阳性 + 中文连写不切分 | 🟠 中高 |

## 二、修复 1：补货冷却分级（`feed/service.py`）

**问题**：`refill_queue` 无论入队多少条都执行 `_last_refill_at[uid] = now()`，
于是「候选池枯竭、入队 0 条」也锁死 30 秒。
压测是机器级速度（20 轮 < 30 秒），冷却把后续补货全拒了。

**修复**：
```python
# core/config.py
QUEUE_REFILL_MIN_GAIN_RATIO = 0.3   # 入队量低于目标 30% 视为"没补到货"
QUEUE_REFILL_RETRY_SEC = 3          # 失败只锁 3 秒重试间隔

# feed/service.py
def _cooldown_ok(user_id):
    now = time.time()
    if (now - _last_refill_at.get(user_id, 0.0)) < QUEUE_REFILL_COOLDOWN_SEC:
        return False                              # 补到货 → 锁 30 秒
    if (now - _last_retry_at.get(user_id, 0.0)) < QUEUE_REFILL_RETRY_SEC:
        return False                              # 没补到 → 只锁 3 秒
    return True
```

**验证**：模拟 20 轮极速刷卡（绕过 30 秒冷却）→ **0 空轮**，队列从 17 稳涨到 57。

## 三、修复 2：冷却软回填（`feed/refill.py`）

**问题**：`recent`（7 天内划过/读过的）被放进硬 `exclude`，
94 个仓库里用户互动过 52 个 → 排除完候选池剩 0。

**修复**：拆成硬排除 + 软排除
```python
exclude = queued | interacted | star_repos   # 硬：绝对不推
soft = recent - exclude                      # 软：降权到 0.4，候选不足时回填

if rid in soft:
    cooled.append((score * 0.4, rid))        # 排序靠后但保留
else:
    scored.append((score, rid))
...
if len(out) < need:                          # 候选不足 → 用冷却项回填
    out += [rid for _, rid in cooled[: need - len(out)]]
```

**效果**：重复率 **70.5% → 53.5%**，唯一仓库 59 → **93**（库内 94 个，基本刷遍）。

## 四、修复 3：领域方向词加权（新增 `dict/domain_terms.txt`）

**问题**：TF-IDF 只看词频，分不清「方向词」和「出现在该方向的通用词」。
实测语音仓库的标签：
```
retrieval-based-voice-conversion-webui
  → [index 0.37, 音色 0.35, 训练 0.31, 素材 0.21, rvc 0.18]
applio
  → [applio 0.33, rvc 0.33, 咬字 0.32, 训练 0.31, 推理 0.23]
```
`rvc` 只有 0.18，被通用词挤出 Top5 → 补货方向变成
`[embedding, llm, applications, gguf, database]`，**语音方向整个丢失**。

**修复**（3 处联动）：

1. 新建 `dict/domain_terms.txt`——150 个方向词 / 10 个领域
   （speech / llm / retrieval / diffusion / training / frontend / database / infra / agent / security）
2. `feed/refill.py` 新增 `_domain_weight()`：命中方向词表 → 权重 ×1.8
   ```python
   weighted = sorted(tags.items(),
                     key=lambda kv: -_domain_weight(str(kv[0]), float(kv[1])))[:5]
   ```
3. `_self_tags_of()` 方向词豁免：`sovits` 在仓库名 `gpt-sovits` 里、
   `rvc` 在 `rvc-project/...` 里，按「项目名派生词」会被误删。
   只要词出现在方向词表里，就按技术术语处理。
   同一口径同步到 `profile/service.py::_repo_self_tags`。

**效果**：

| 仓库 | 修复前 Top5 | 修复后 Top5 |
|---|---|---|
| retrieval-based-voice-conversion-webui | index, 音色, 训练, 素材, rvc | index, **rvc**, model, rate, 48k |
| gpt-sovits | gpt, sovits, 音色, 音频, 模块 | gpt, **sovits**, **音频**, token, 韵律 |
| coqui-ai/TTS | — | xtts, **克隆**, coqui, tts, vits |
| so-vits-svc | — | **rvc 0.83**, **vits 0.5**, hubert, svc |

画像里语音词从 **0 个 → 5 个**（rvc / vits / tts / 克隆 / sovits）。

## 五、修复 4：搜索词边界 + 中文切分（`api/search_service.py`）

**问题 A：子串假阳性**
搜 `Ai` 命中 `tailwindlabs/tailwindcss`——owner 名里含 "ai"。

```python
_WHOLE_WORD_MAX = 3

def _name_contains(hay, needle, *, whole=False):
    """短词必须整词命中。"""
    if whole or len(needle) <= _WHOLE_WORD_MAX:
        return needle in _NAME_SPLIT.split(hay)
    return needle in hay
```

**问题 B：中文连写不切分**
搜「向量数据库」→ 0 结果。`tech_terms.txt` 把它注册成了整词，
`jieba.cut()` 不切；而 `_WORD_SPLIT` 对中文无效。

```python
# ⚠️ 必须用 cut_for_search，不能用 cut
for w in jieba.cut_for_search(q):    # '向量数据库' → 向量/数据/数据库/向量数据库
    _add(w)
```

**问题 C：低分项混入**
`Ai` 结果里混进 `microsoft/vscode`（1.27 分，靠 quality_score 兜底），
而真正相关的 `newbie-ai/tiny-embed` 是 4.23 分。

```python
# core/config.py
SEARCH_MIN_SCORE_RATIO = 0.45   # 低于最高分 45% 不展示

    scored = strong
```

## 六、修复 5：词典文件格式污染（3 个文件）

## 九、仍存在的限制（不是 bug）

1. **重复率 53.5% 是数据规模决定的**：94 个仓库刷 200 条，物理上必然重复。
   接入真实爬虫后这个数字会自然下降。
2. **队列在极速压测下仍会归零**：补货成功后锁 30 秒冷却。
   真实用户 30 秒刷不完 60 条，所以冷却是对的；
   压测是机器速度，会顶到冷却上限，此时靠实时保底兜住。
3. **中文标签覆盖率低**：仓库 README 以英文为主，
   中文查询主要靠 `topics` + README 正文匹配，召回不如英文。
