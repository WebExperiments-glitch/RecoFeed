一、核心认知纠正：Monolith ≠ 抖音算法

这是整个调研里最重要的一条，先把它钉死，不然后面架构会走偏。

社区里流传「抖音推荐算法开源了，就在 GitHub 上」。这句话半真半假1：

字节跳动的 monolith 仓库里有什么： ✅ 碰撞无关嵌入表（collisionless embedding table） ✅ 实时训练架构（分钟级更新模型） ✅ 分布式训练 + 在线服务框架 ❌ 抖音实际用了哪些特征信号 ❌ 每个信号的权重是多少 ❌ 排序公式长什么样

打个比方：字节公开了发动机的图纸，但没公开方向盘怎么打1。Monolith 是「引擎」，不是「策略」。

Monolith 的 README 标题现在已改成 "A Lightweight Recommendation System"，最后提交在 2023-11，社区反馈它在 2025-10 已被归档为只读1。它能看，但不能作为项目依赖。

对我们的意义：Monolith 可以读它的设计理念（实时性 + 无碰撞嵌入），但不要试图编译它（Bazel + TensorFlow 老版本，Linux only，社区反馈大量 segfault2）。

对比一下三家的公开程度1：

平台 公开方式 你能读到什么 读不到什么
X (Twitter) 真实代码开源 具体评估哪些特征 只有权重值保密
TikTok / 抖音 只开源引擎 为什么快 它评估什么
Instagram 代码闭源，官方文档说明 各界面信号及其重要性排序 实现

二、抖音推流机制：公开可查的真相

抖音官方在 2020-06-18 的 newsroom 里公开说明过推荐系统的工作方式1：

官方明确表态：粉丝数不是直接影响因素。信号分三大类： ① 你的行为（完播、点赞、评论、分享、关注） ② 视频信息（音频、文案、话题标签） ③ 设备与账号设置（语言、地区、设备类型）

而技术圈公认的抖音式信息流的核心逻辑是 「多级漏斗 + 实时反馈」：

┌──────────────────────────────────┐ 百万级仓库池 → │ ① 召回 Recall │ 千级候选 │ 多路并行：协同过滤/标签/热榜/关注 │ └──────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ 千级候选 → │ ② 粗排 Pre-Rank │ 百级 │ 轻量模型快速过滤 │ └──────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ 百级 → │ ③ 精排 Rank │ 十几条 │ 重模型 + 多目标融合（完播/点赞…） │ └──────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ 十几条 → │ ④ 重排 Re-Rank │ 最终 Feed │ 打散/多样性/探索位/去重 │ └──────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ 用户交互 → 实时回写 → 影响下一次 └──────────────────────────────────┘

这个漏斗就是我们项目要仿的东西。 好消息是：这套范式在开源界有完全可读的实现。

四、GitHub 特有的推荐信号（这决定了项目成败）

GitHub 场景和短视频本质不同： - 短视频是即时消费，仓库是工具/知识，用户需要"找到有用的东西" - 短视频没有"过时"问题，仓库有（依赖过期、停止维护） - 优质仓库可能 半年 0 star，但代码质量极高 —— 这正是我们要解决的痛点

4.1 可用的信号与评分模型

调研到两个直接相关的开源实现：

① jasperan/discover-github —— 多信号突围评分引擎3

信号 权重 衡量什么
Star Velocity 30% 每日新增 star（对数尺度）
Freshness 15% 最后 push 距今时间
Community Health 15% 贡献者数、issue、CI 流水线
Adoption Signal 15% fork/star 比、watcher、homepage
Activity Momentum 15% 近期 commit + 年龄校正的 star 加成
Documentation Quality 10% README 长度、License、topics、描述

分档：S(80+) → A(65+) → B(50+) → C(35+) → D(<35) License：UPL 1.0 + Apache 2.0 双协议 ✅ 可安全参考

💡 注意它第一个信号就是 "Star Velocity" 而不是总 star 数 —— 这正是解决「老仓库没人看」的关键思路。

② 通用热度公式（社区实践）4

热度分数 = (今日 star - 昨日 star) / 时间衰减因子 # 没有历史快照时的降级方案： 初始热度 = log(当前 star 数) / (创建至今小时数 + 1)

这个公式的意义：一个 24 小时内获得 100 star 的新项目，比一个存在一年总共 200 star 的项目在"今日"更热。 取对数是为了防止超级项目永远霸榜。

4.2 「唤醒沉睡仓库」的原创算法思路

这是本项目区别于所有现有 GitHub Trending 工具的核心创新点：

传统 Trending：按 star 总数排序 → 老牌大项目霸榜 → 冷门优质仓库永远没机会 我们的方案：给「被遗忘但优质」的仓库专门开一条召回通路 遗忘分（Forgotten Score）= (代码质量分) # 有 CI / 有测试 / README 完整 / 最近有 commit × (年龄衰减) # 越久没被人看到，越该被推荐 × (低曝光惩罚) # star 少的仓库加分 ← 与商业平台完全相反！ × (活跃维护标记) # 最近 push 过 = 不是真死库

这等于做了一个「反马太效应」的推荐器：商业平台追求让热门更热，我们要做的是让遗珠浮上来。这个理念本身就是项目最好的宣传故事（正好呼应你的"让开源社区变得有活力"）。

4.3 License 合规检测（必须做）

推荐一个仓库给用户，License 是安全指标的一部分，不能推荐一个 GPL 的库给要做商业产品的人：

License 风险分级（用于推荐时的"安全提示"标签）： 安全 🟢 MIT / Apache-2.0 / BSD / ISC / UPL 注意 🟡 MPL-2.0 / LGPL / EPL 风险 🔴 GPL-2.0 / GPL-3.0 / AGPL-3.0 （传染性强） 未知 ⚫ 无 LICENSE 文件（默认保留所有权利）

discover-github 的 Documentation Quality 信号里把 license 作为一个子项，我们的方案应该把它提升为核心安全标签。

快手 OpenOneRec —— 值得重点看一眼（学术前沿）

这是调研里技术含量最高的项目：

项目信息 内容
仓库 Kuaishou-OneRec/OpenOneRec
License 代码 Apache-2.0 ✅ / ⚠️ 模型权重另有单独协议，需单独审查
模型 OneRec-1.7B / 8B（基于 Qwen3），另有 Pro 版本用快手内部千亿 token 语料
数据 RecIF-Bench：1 亿交互 / 20 万用户，覆盖短视频、广告、电商三域
核心思路 把推荐重构为序列建模 —— item 用分层向量量化（RVQ）转成 "Itemic Tokens"，然后交给 LLM 做 next-token prediction

它给我们的启示（不一定用得上的，但思路值钱）：

传统的推荐是「召回→排序」的漏斗；OpenOneRec 直接把推荐变成 "给 LLM 一段用户行为序列，让它预测下一个 item"。

对应到我们的项目：

输入：用户最近看过的仓库序列 + 用户画像 [repo:torch, repo:vite, repo:three.js, ...] 输出：下一个可能感兴趣的仓库

💡 但要注意：这东西需要 GPU 训练 + 大量数据，对本地/个人项目过重。建议：理念上借鉴（序列建模、LLM 生成推荐理由），实现上不上这套模型。

真正低成本能落地的是它的 Layer 3「推理能力」—— 让模型生成"为什么推荐给你"的自然语言理由。这个用现成的 LLM API（你已有的 DeepSeek API 经验）就能做，而且体验极好：推荐流里每张卡片下面写一句 "因为你最近在看 3D 渲染相关的仓库，这个项目的 WebGL 实现很巧"。

TagCF（快手 + 武大，NeurIPS 2025）的思路也很有价值：从"猜你喜欢什么内容"升级到"理解你是谁" —— 引入 user role（用户角色） 建模。"啤酒-新晋奶爸-尿布"的经典案例：不是啤酒和尿布相关，而是背后有"新晋奶爸"这个用户角色在起作用。这也解释了为什么强关联建模能突破信息茧房。

映射到我们：不是「Python 仓库和 ML 仓库相关」，而是「这个用户是个在做 LLM 应用的学生开发者」。

7.4 冷启动策略（老仓库 & 新仓库都要推）

用户明确要求「老仓库或新仓库都要推」，这需要多路召回并行：

召回通路 面向 逻辑
① 兴趣召回 主力 协同过滤 / 标签匹配（用户 topics ↔ 仓库 topics）
② 遗珠召回 ⭐ 本项目特色 forgotten_score 高分但曝光极少的仓库
③ 热榜召回 大众 Star Velocity 榜（不是总 star 榜）
④ 新鲜召回 新仓库 created_at 近 7 天 + 质量分达标
⑤ 关注召回 老用户 已 follow 的 owner 的新动作
⑥ 探索召回 所有人 随机 + 多样性打散（15% 槽位）
⑦ 相似召回 有历史 "看了 A 的人也在看 B"（item-based CF）

冷启动三重保障： 1. 新用户：先给 3~5 个「热门 + 质量高 + 覆盖不同语言」的仓库摸底，快速建立初始画像 2. 新仓库：没有行为数据 → 用 内容特征（topics / README embedding）走内容召回，而不是协同过滤 3. 老仓库：forgotten_score 通路专门覆盖
