> **调研目标**：做一套「仿抖音的信息流推流平台」，但推的不是短视频，而是 **GitHub 仓库**。
> 让那些无人访问、被遗忘的优质开源仓库重新获得曝光。
>
> 版本：v0.1（调研阶段）

## 0. 先说结论（TL;DR）

| 问题 | 结论 |
|---|---|
| 抖音推流算法能直接抄吗？ | ❌ 不能。抖音没开源推荐算法，开源的是**引擎**（Monolith），不是**策略权重** |

## 一、核心认知纠正：Monolith ≠ 抖音算法

这是整个调研里**最重要的一条**，先把它钉死，不然后面架构会走偏。

社区里流传「抖音推荐算法开源了，就在 GitHub 上」。这句话**半真半假**[^1]：

```
字节跳动的 monolith 仓库里有什么：
  ✅ 碰撞无关嵌入表（collisionless embedding table）
  ✅ 实时训练架构（分钟级更新模型）
  ✅ 分布式训练 + 在线服务框架
  ❌ 抖音实际用了哪些特征信号
  ❌ 每个信号的权重是多少
  ❌ 排序公式长什么样
```

打个比方：**字节公开了发动机的图纸，但没公开方向盘怎么打**[^1]。Monolith 是「引擎」，不是「策略」。

> Monolith 的 README 标题现在已改成 *"A Lightweight Recommendation System"*，最后提交在 2023-11，社区反馈它在 2025-10 已被归档为只读[^1]。**它能看，但不能作为项目依赖。**

**对我们的意义**：Monolith 可以读它的设计理念（实时性 + 无碰撞嵌入），但**不要试图编译它**（Bazel + TensorFlow 老版本，Linux only，社区反馈大量 segfault[^2]）。

对比一下三家的公开程度[^1]：

| 平台 | 公开方式 | 你能读到什么 | 读不到什么 |
|---|---|---|---|
| X (Twitter) | 真实代码开源 | 具体评估哪些特征 | 只有权重值保密 |
| TikTok / 抖音 | 只开源引擎 | 为什么快 | 它评估什么 |
| Instagram | 代码闭源，官方文档说明 | 各界面信号及其重要性排序 | 实现 |

## 二、抖音推流机制：公开可查的真相

抖音官方在 2020-06-18 的 newsroom 里公开说明过推荐系统的工作方式[^1]：

> 官方明确表态：**粉丝数不是直接影响因素**。信号分三大类：
> ① 你的行为（完播、点赞、评论、分享、关注）
> ② 视频信息（音频、文案、话题标签）
> ③ 设备与账号设置（语言、地区、设备类型）

而技术圈公认的抖音式信息流的核心逻辑是 **「多级漏斗 + 实时反馈」**：

```
                    ┌──────────────────────────────────┐
   百万级仓库池  →   │ ① 召回 Recall                     │  千级候选
                    │   多路并行：协同过滤/标签/热榜/关注  │
                    └──────────────────────────────────┘
                                    ↓
                    ┌──────────────────────────────────┐
   千级候选      →   │ ② 粗排 Pre-Rank                   │  百级
                    │   轻量模型快速过滤                  │
                    └──────────────────────────────────┘
                                    ↓
                    ┌──────────────────────────────────┐
   百级          →   │ ③ 精排 Rank                       │  十几条
                    │   重模型 + 多目标融合（完播/点赞…）   │
                    └──────────────────────────────────┘
                                    ↓
                    ┌──────────────────────────────────┐
   十几条        →   │ ④ 重排 Re-Rank                    │  最终 Feed
                    │   打散/多样性/探索位/去重           │
                    └──────────────────────────────────┘
                                    ↓
                    ┌──────────────────────────────────┐
                       用户交互 → 实时回写 → 影响下一次    
                    └──────────────────────────────────┘
```

**这个漏斗就是我们项目要仿的东西。** 好消息是：这套范式在开源界有**完全可读的实现**。

## 三、核心参考实现：`SOCIAL-ALGORITHM`

调研中发现的**最贴合我们需求**的仓库。

| 项目信息 | 内容 |
|---|---|
| 仓库 | [`blacckoscar/SOCIAL-ALGORITHM`](https://github.com/blacckoscar/SOCIAL-ALGORITHM) |
| 项目名 | FeedAlgo — Addictive Feed Algorithm (TikTok / Instagram style) |
| 语言 | Go（全栈，含 JWT 鉴权 + SQLite） |
| License | ⚠️ **仓库没有 LICENSE 文件** → 默认保留所有权利，**只能读思路，不能抄代码** |
| 状态 | 单次 initial commit（2026-02），玩具项目 |
| 可读性 | ⭐⭐⭐⭐⭐ 算法写得极清楚，README 直接给出了完整公式 |

### 它的打分算法（关键！直接可借鉴）

```python
# ① 互动率（engagement rate）—— 越高越"上瘾"
eng = (w_like*likes + w_comment*comments + w_share*shares + w_completion*completion) / (views + 1)
# completion = 总观看时长 / (视频时长 × 播放次数)，上限封顶
# → 高完播率的内容排名更高，这就是"抖音味"的来源

# ② 时效性（recency）—— 指数衰减
recency = exp(-lambda * hours_old)     # lambda=0.08，越新分越高

# ③ 亲近度（affinity）—— 跟你互动过的作者加权
if 用户之前赞过/看过这个作者:
    score *= 1 + affinity_weight * log(1 + affinity_sum)   # affinity_weight=2.0

# ④ 探索位（exploration）—— 打散信息茧房
15% 的 feed 槽位替换成随机发现内容

# ⑤ 去重（deduplication）
登录用户已看过的 post_id 从候选池排除
```

### 迁移到「推荐 GitHub 仓库」的映射表 ⭐

这是本报告的核心产出之一：

| 抖音概念 | 本项目对应物 | 数据来源 |
|---|---|---|
| 视频 (video) | **GitHub 仓库** | GitHub API / TrendPulse 爬虫 |
| 完播率 (completion) | **README 阅读完成度** / 停留时长 / 点击 Releases、Issues 的深度行为 | 前端埋点 |
| 点赞 (like) | **网页端点赞**（用户描述的"网页端记录"） | 自建 SQL |
| 收藏 (collect) | **GitHub Star**（用户描述："收藏对应 GitHub 星星"） | GitHub API |
| 评论 (comment) | **GitHub Discussion / Issue**（用户描述） | GitHub API |
| 分享 (share) | 站外分享链接、复制仓库地址 | 前端埋点 |
| 作者 affinity | **仓库 owner / 组织** 维度加权 | 自建 SQL |
| 热度时效 | **Star 增长速度**（不是总 star 数！） | 两次快照差值 |
| 冷启动 | 新仓库没有 star → 用 **Star Velocity（单位时间增速）** | 见下节 |

> ⚠️ **关键设计难点**：抖音用「完播率」当核心信号，但**仓库没有"完播"概念**。我们必须重新定义等价信号 —— 这是这个项目真正的原创价值点。候选方案见第七章。

## 四、GitHub 特有的推荐信号（这决定了项目成败）

GitHub 场景和短视频**本质不同**：
- 短视频是**即时消费**，仓库是**工具/知识**，用户需要"找到有用的东西"
- 短视频没有"过时"问题，仓库有（依赖过期、停止维护）
- 优质仓库可能 **半年 0 star**，但代码质量极高 —— 这正是我们要解决的痛点

### 4.1 可用的信号与评分模型

调研到两个直接相关的开源实现：

**① `jasperan/discover-github`** —— 多信号突围评分引擎[^3]

| 信号 | 权重 | 衡量什么 |
|---|---|---|
| **Star Velocity** | **30%** | 每日新增 star（对数尺度） |
| Freshness | 15% | 最后 push 距今时间 |
| Community Health | 15% | 贡献者数、issue、CI 流水线 |
| Adoption Signal | 15% | fork/star 比、watcher、homepage |
| Activity Momentum | 15% | 近期 commit + 年龄校正的 star 加成 |
| Documentation Quality | 10% | README 长度、License、topics、描述 |

分档：`S(80+) → A(65+) → B(50+) → C(35+) → D(<35)`
License：**UPL 1.0 + Apache 2.0 双协议** ✅ 可安全参考

> 💡 **注意它第一个信号就是 "Star Velocity" 而不是总 star 数** —— 这正是解决「老仓库没人看」的关键思路。

**② 通用热度公式（社区实践）**[^4]

```
热度分数 = (今日 star - 昨日 star) / 时间衰减因子

# 没有历史快照时的降级方案：
初始热度 = log(当前 star 数) / (创建至今小时数 + 1)
```

> 这个公式的意义：**一个 24 小时内获得 100 star 的新项目，比一个存在一年总共 200 star 的项目在"今日"更热。** 取对数是为了防止超级项目永远霸榜。

### 4.2 「唤醒沉睡仓库」的原创算法思路

这是本项目**区别于所有现有 GitHub Trending 工具**的核心创新点：

```
传统 Trending：按 star 总数排序 → 老牌大项目霸榜 → 冷门优质仓库永远没机会

我们的方案：给「被遗忘但优质」的仓库专门开一条召回通路

遗忘分（Forgotten Score）=
    (代码质量分)      # 有 CI / 有测试 / README 完整 / 最近有 commit
  × (年龄衰减)        # 越久没被人看到，越该被推荐
  × (低曝光惩罚)      # star 少的仓库加分 ← 与商业平台完全相反！
  × (活跃维护标记)    # 最近 push 过 = 不是真死库
```

> 这等于做了一个**「反马太效应」的推荐器**：商业平台追求让热门更热，我们要做的是让**遗珠浮上来**。这个理念本身就是项目最好的宣传故事（正好呼应你的"让开源社区变得有活力"）。

### 4.3 License 合规检测（必须做）

推荐一个仓库给用户，**License 是安全指标的一部分**，不能推荐一个 GPL 的库给要做商业产品的人：

```
License 风险分级（用于推荐时的"安全提示"标签）：
  安全 🟢  MIT / Apache-2.0 / BSD / ISC / UPL
  注意 🟡  MPL-2.0 / LGPL / EPL
  风险 🔴  GPL-2.0 / GPL-3.0 / AGPL-3.0 （传染性强）
  未知 ⚫  无 LICENSE 文件（默认保留所有权利）
```

`discover-github` 的 `Documentation Quality` 信号里把 license 作为一个子项，我们的方案应该把它**提升为核心安全标签**。

- `react-intersection-observer` 自动播放/暂停

- Cursor-based 分页（`nextCursor`），不用 offset

### 5.2 毛玻璃 & 高级动画技术选型 ⭐

| 库 | 体积 | License | 商用 | 用途 |
|---|---|---|---|---|
| **GSAP** | ~23KB core | 标准"免费"许可 | ✅ **100% 免费含商用**（Webflow 收购后全部插件免费：SplitText / MorphSVG / ScrollTrigger）[^5] | 复杂时间轴、滚动驱动动画、文字分割 |
| **Motion**（原 Framer Motion） | 34KB / LazyMotion 4.6KB | MIT | ✅ | React 声明式动画、布局动画、手势、`AnimatePresence` |
| **Lenis** | ~2KB | MIT | ✅ | 丝滑滚动基底，Awwwards 获奖站标配 |
| Locomotive Scroll v5 | 9.4KB | MIT | ✅ | 视差，v5 基于 Lenis |
| Theatre.js | 生产仅 core | Apache-2.0 | ✅ | 电影级 3D 关键帧，带浏览器内编辑器 |

**性能铁律**（做毛玻璃必须遵守，否则掉帧）[^6]：

```css
/* 只有这 4 个属性是 GPU 合成，不触发 layout / paint */
transform, opacity, filter, backdrop-filter  ← 动画只动这 4 个
```

```css
/* ❌ 触发 reflow */
.box:hover { width: 200px; left: 100px; }
/* ✅ GPU 合成 */
.box:hover { transform: translateX(100px) scale(1.05); }
```

其他技巧：
- `content-visibility: auto` 给首屏以下区块 → 跳过离屏渲染，首屏大幅提升
- `IntersectionObserver` + 动态 `import()` → 重型库（GSAP）只在区块进入视口时才加载
- 图片：`AVIF > WebP > JPEG` 级联，AVIF 同画质小 ~50%
- 字体：`font-display: swap`
- Speculation Rules API 预渲染 → 近乎瞬时的页面跳转

### 5.3 2026 设计趋势（正好契合你的需求）[^6]

- **Apple Liquid Glass**（WWDC 2025 发布）已验证 glassmorphism 是长期方向，不是一时风潮
- **Dark Glassmorphism**：深色底 + 环境渐变光晕（ambient gradient orbs）→ 被列为 2026 标志性 UI 手法
- 空间设计原则（visionOS）下沉到平面：**z 轴分层 + 视差 + 光照 + 毛玻璃** → 无需硬件也能做出纵深感
- 超大字重动效排版（kinetic type）当主视觉
- 有机形状 / 反网格布局 / 柔和渐变

> **给本项目的 UI 方向建议**：GitHub 是"冷色 + 代码感 + 信息密度"，Apple 是"留白 + 大圆角 + 玻璃层 + 克制动效"。
> 融合方式 = **深色玻璃卡片作为仓库卡片的容器**（Dark Glassmorphism），背景放缓慢流动的渐变光晕，卡片滚动时用 GSAP ScrollTrigger 做轻微 3D 倾斜视差。这既像抖音滑动，又有 Apple 高级感，还保留 GitHub 的信息层次。

### 快手 OpenOneRec —— 值得重点看一眼（学术前沿）

这是调研里**技术含量最高**的项目：

| 项目信息 | 内容 |
|---|---|
| 仓库 | [`Kuaishou-OneRec/OpenOneRec`](https://github.com/Kuaishou-OneRec/OpenOneRec) |
| License | **代码 Apache-2.0** ✅ / ⚠️ **模型权重另有单独协议，需单独审查** |
| 模型 | OneRec-1.7B / 8B（基于 Qwen3），另有 Pro 版本用快手内部千亿 token 语料 |
| 数据 | RecIF-Bench：**1 亿交互 / 20 万用户**，覆盖短视频、广告、电商三域 |
| 核心思路 | **把推荐重构为序列建模** —— item 用分层向量量化（RVQ）转成 "Itemic Tokens"，然后交给 LLM 做 next-token prediction |

**它给我们的启示**（不一定用得上的，但思路值钱）：

传统的推荐是「召回→排序」的漏斗；OpenOneRec 直接把推荐变成 **"给 LLM 一段用户行为序列，让它预测下一个 item"**。

对应到我们的项目：
```
输入：用户最近看过的仓库序列 + 用户画像
     [repo:torch, repo:vite, repo:three.js, ...]
输出：下一个可能感兴趣的仓库
```

> 💡 **但要注意**：这东西需要 GPU 训练 + 大量数据，**对本地/个人项目过重**。建议：**理念上借鉴（序列建模、LLM 生成推荐理由），实现上不上这套模型**。
>
> 真正低成本能落地的是它的 **Layer 3「推理能力」—— 让模型生成"为什么推荐给你"的自然语言理由**。这个用现成的 LLM API（你已有的 DeepSeek API 经验）就能做，而且体验极好：推荐流里每张卡片下面写一句 "因为你最近在看 3D 渲染相关的仓库，这个项目的 WebGL 实现很巧"。

TagCF（快手 + 武大，NeurIPS 2025）的思路也很有价值：**从"猜你喜欢什么内容"升级到"理解你是谁"** —— 引入 **user role（用户角色）** 建模。"啤酒-新晋奶爸-尿布"的经典案例：不是啤酒和尿布相关，而是背后有"新晋奶爸"这个**用户角色**在起作用。这也解释了为什么强关联建模能**突破信息茧房**。

映射到我们：不是「Python 仓库和 ML 仓库相关」，而是「**这个用户是个在做 LLM 应用的学生开发者**」。

## 七、架构设计建议

### 7.2 数据表设计（SQL 方案）

```sql
-- 用户
users(id, username, password_hash, avatar_url, github_token_enc,
      created_at, last_active_at)

-- 仓库（核心实体）
repos(id, owner, name, full_name UNIQUE, description, readme_md,
      language, topics_json, license_spdx, homepage,
      stars, forks, watchers, open_issues, contributors_count,
      has_ci, has_tests, created_at_gh, pushed_at_gh,
      -- 我们自己算的分
      forgotten_score REAL, quality_score REAL,
      first_seen_at, last_refreshed_at)

-- star 历史快照 ← 算 Star Velocity 的关键，没有它就只能用降级公式
repo_star_snapshots(id, repo_id, stars, captured_at)
  INDEX (repo_id, captured_at)

-- 用户行为（推流算法唯一的数据来源）
user_events(id, user_id, repo_id, event_type, weight,
            dwell_ms, scroll_depth, source_channel, created_at)
  INDEX (user_id, created_at)
  INDEX (repo_id, event_type)
-- event_type: impression|view|like|unlike|detail_open|star_click|
--             comment|share|search|follow_owner|skip
-- weight: 每个事件的权重（见 7.3）

-- 点赞（用户要求的"网页端记录"）
likes(user_id, repo_id, created_at, PRIMARY KEY(user_id, repo_id))

-- 收藏 = 同步 GitHub star
stars(user_id, repo_id, gh_starred BOOLEAN, synced_at,
      PRIMARY KEY(user_id, repo_id))

-- 评论 = 同步 GitHub Discussion/Issue
comments(id, repo_id, user_id, gh_discussion_id, gh_comment_id,
         body, created_at)

-- 用户兴趣画像（定期重算）
user_profiles(user_id, top_languages_json, top_topics_json,
              affinity_owners_json, updated_at)

-- 推荐曝光记录（用于去重 + 效果分析）
feed_impressions(id, user_id, repo_id, rank, score,
                 channel, shown_at, clicked_at)
```

### 7.3 事件权重表（仿抖音的核心参数）

```python
EVENT_WEIGHTS = {
    "impression":    0.0,    # 只曝光不点击 = 负信号（分母）
    "skip":         -1.0,    # 划走 = 强负反馈
    "view":          0.5,    # 打开详情
    "dwell_10s":     1.0,    # 停留 10 秒
    "read_readme":   2.0,    # 滚动 README 超过 50% ← 我们的"完播率"
    "open_files":    2.5,    # 打开了源码文件
    "like":          4.0,    # 网页端点赞
    "star_click":    6.0,    # 点了去 GitHub star ← 我们的"收藏"
    "comment":       5.0,    # 评论
    "share":         5.0,    # 分享
    "follow_owner":  7.0,    # 关注作者 ← 最强正反馈
}
```

### 7.4 冷启动策略（老仓库 & 新仓库都要推）

用户明确要求「老仓库或新仓库都要推」，这需要**多路召回**并行：

| 召回通路 | 面向 | 逻辑 |
|---|---|---|
| ① 兴趣召回 | 主力 | 协同过滤 / 标签匹配（用户 topics ↔ 仓库 topics） |
| ② **遗珠召回** | ⭐ 本项目特色 | `forgotten_score` 高分但曝光极少的仓库 |
| ③ 热榜召回 | 大众 | Star Velocity 榜（不是总 star 榜） |
| ④ 新鲜召回 | 新仓库 | `created_at` 近 7 天 + 质量分达标 |
| ⑤ 关注召回 | 老用户 | 已 follow 的 owner 的新动作 |
| ⑥ 探索召回 | 所有人 | 随机 + 多样性打散（15% 槽位） |
| ⑦ 相似召回 | 有历史 | "看了 A 的人也在看 B"（item-based CF） |

**冷启动三重保障**：
1. **新用户**：先给 3~5 个「热门 + 质量高 + 覆盖不同语言」的仓库摸底，快速建立初始画像
2. **新仓库**：没有行为数据 → 用 **内容特征**（topics / README embedding）走内容召回，而不是协同过滤
3. **老仓库**：`forgotten_score` 通路专门覆盖

## 九、竞品/同类调研（我们和它们的区别）

| 产品 | 形式 | 我们的差异点 |
|---|---|---|
| GitHub Trending | 榜单页 | 我们是个性化信息流，且专门救"遗珠" |
| GitHub Explore | 编辑推荐 | 我们是算法驱动 + 用户行为反馈 |
| Star History / OSS Insight | 数据图表 | 我们不分析，我们**分发** |
| Hacker News / Product Hunt | 榜单 | 我们按个人兴趣，不按当日热榜 |
| `jasperan/discover-github` | CLI 工具 | 它是给你生成推文，我们是产品化 Feed |
| TrendPulse（你自己的） | Trending 分析平台 | TrendPulse 是**数据侧**，本项目是**分发侧** —— **可以复用爬虫层！** |

> 💡 **重要协同点**：你的 TrendPulse 已经有 GitHub trending 数据抓取 + 后端 + SQLite 了。本项目可以直接把它当作 **数据供应层**（召回池的来源），避免重复造轮子。建议把本项目做成 TrendPulse 的"消费端"，或者抽一个共享的 `github-data-service`。

## 十、下一步：A / B / C 三条路

调研阶段结束，接下来该定方向了。给你三个选项：

### 选项 A：最小可行版（推荐起步）✅

**周期**：短
**做什么**：
1. 用 TrendPulse 的爬虫层产出一个仓库池（先用 JSON 也行，不急着上 SQL）
2. 后端只实现**一路召回 + 一个加权打分公式**（就用 SOCIAL-ALGORITHM 那套改写）
3. 前端 React + Tailwind + **GSAP 毛玻璃卡片**，做垂直滑动的信息流
4. 只做 4 个行为：曝光 / 停留 / 点赞 / 跳转 star

**优点**：快速看到效果，UI 先惊艳起来，算法后续迭代
**风险**：几乎没有

### 选项 B：完整架构版

**周期**：中长
**做什么**：按第七章的架构全量落地 —— 7 路召回 + 四级漏斗 + 用户画像 + 埋点体系 + 后台任务 + 完整 SQL 表
**优点**：一步到位，符合"企业级做法"要求
**风险**：前期投入大，没见到效果前容易失去动力（你自己也说了"开发者兴趣消亡"是最大敌人 😄）

### 选项 C：先做算法原型

**周期**：短
**做什么**：纯命令行/Python，先把**召回+排序算法**跑通，用假数据验证 `forgotten_score` 能不能真的把遗珠仓库挑出来
**优点**：验证核心创新点是否成立，成本最低
**风险**：没有 UI，看不到"抖音感"
